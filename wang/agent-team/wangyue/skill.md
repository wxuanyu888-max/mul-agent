# Skill Tree - 上下文感知的能力披露

## 核心理念

**能力披露应该基于上下文理解，而不是机械的关键词匹配。**

---

## 能力架构

### 第一层：基础能力（始终可用）

这些能力无需用户记忆命令格式，自动触发：

| 意图模式 | 自动触发能力 | 示例输入 | 上下文增强 |
|---------|-------------|---------|-----------|
| 问候 | 友好响应 | "你好", "hi" | 参考历史对话风格 |
| 问题 | 直接回答 | "这个项目怎么样" | 检索项目相关信息 |
| 命令格式 | bash 执行 | "ls -la", "$ cat file" | 理解隐式命令意图 |
| 求助 | 帮助菜单 | "help", "帮助" | 根据用户水平调整详细程度 |

**上下文感知的关键**：
- 问候时参考历史对话，保持连贯性
- 回答问题时检索短期/长期记忆中的相关信息
- 识别隐式命令意图（如"看看这个文件"→bash）

### 第二层：协作能力（情境触发）

当上下文表现出协作需求时自动披露：

| 意图模式 | 能力 | 触发条件 | 上下文判断 |
|---------|------|---------|-----------|
| 创建类词汇 | create_user | 用户说"创建/新建" | + "Agent/助手/bot" 等目标词 |
| 团队类词汇 | create_team | 用户提到"团队/组队" | + 协作/分工等语义 |
| 记忆类词汇 | memory | 用户提到"记住/记忆" | + 具体内容/查询意图 |
| 对话类词汇 | chat | 用户提到"和 xx 对话" | + Agent 名称/角色 |

**上下文感知的关键**：
- 不是简单关键词匹配，而是理解语义
- 参考历史对话，判断用户是否有协作经验
- 根据任务复杂度，主动建议使用协作能力

### 第三层：专家能力（按需披露）

当用户明确请求或系统评估需要时披露：

| 能力 | 触发条件 | 披露方式 |
|------|---------|---------|
| heart (自省) | 用户明确输入"heart/evolve" | 直接执行 |
| network_delegate | 任务复杂度 > 阈值 | 主动建议委派 |
| network_broadcast | 需要多 Agent 协作 | 主动建议广播 |
| token_usage | 用户查询使用情况 | 直接展示 |

**复杂度评估公式**：
```
complexity_score =
  (task_steps * 0.3) +
  (required_expertise * 0.3) +
  (context_ambiguity * 0.2) +
  (user_stress_level * 0.2)
```

## 上下文感知的路由决策

### 决策流程

```
用户输入
    │
    ▼
1. 模式匹配（快速路径）
    ├── 空输入 → response
    ├── 明确命令 → bash
    ├── 问候语 → uncertain (LLM 生成)
    ├── 帮助请求 → response
    ├── 创建/团队 → create_user/create_team
    ├── 记忆相关 → memory
    ├── 自省/进化 → heart
    ├── 对话其他 Agent → chat
    └── 无法匹配 → 进入下一层
    │
    ▼
2. 上下文分析（LLM 辅助）
    ├── 检索短期记忆（最近交互）
    ├── 检索长期记忆（历史方案）
    ├── 分析真实意图
    └── 生成响应内容
    │
    ▼
3. 执行并学习
    ├── 执行路由动作
    ├── 记录到记忆
    └── 更新决策模型
```

### 隐式意图识别

不只是匹配关键词，而是理解语义：

| 用户输入 | 真实意图 | 路由 |
|---------|---------|------|
| "看看这个"（上文有文件） | 查看文件内容 | bash (cat) |
| "项目结构怎么样" | 分析项目结构 | bash (find/tree) |
| "有哪些依赖" | 查看依赖列表 | bash (pip list/cat package.json) |
| "这个功能怎么实现" | 寻求实现建议 | uncertain → LLM 分析 |
| "交给专业人士处理" | 委派任务 | chat → network_delegate |

## 能力解锁条件

```yaml
level_1_unlocked: always
level_2_unlocked:
  conditions:
    - user_has_created_agent: true
    - OR conversation_length > 10
    - OR user_shows_collaborative_intent: true
level_3_unlocked:
  conditions:
    - user_explicitly_requests: true
    - OR agent_complexity_score > 0.7
    - OR task_requires_specialist: true
```

## 记忆驱动的能力优化

### 从历史学习

每次交互后记录：
- 用户使用的词汇和表达方式
- 任务类型和复杂度
- 选择的路由和结果
- 用户的反馈（正面/负面）

### 个性化适配

根据记忆调整：
- 响应风格（简洁 vs 详细）
- 能力披露时机（主动 vs 被动）
- 帮助菜单的详细程度
- 推荐命令的格式

## 决策示例

### 示例 1：上下文指代
```
上文：用户提到"config.json 文件"
当前："这个文件内容是什么？"
→ 检索短期记忆 → 识别"这个文件"=config.json
→ bash (cat config.json)
```

### 示例 2：隐式命令
```
用户："项目结构怎么样？"
→ 规则无法匹配 → uncertain
→ LLM 分析意图 → 用户想看项目结构
→ bash (find . -type f | head -20)
```

### 示例 3：复杂度评估
```
用户："帮我实现一个完整的用户认证系统"
→ 规则无法匹配 → uncertain
→ LLM 分析 + 复杂度评估 → 复杂任务
→ 主动建议：委派给 coder Agent
```

### 示例 4：历史参考
```
用户："像上次那样分析这个项目"
→ 检索长期记忆 → 查找"上次"的分析方式
→ 复用历史解决方案
→ bash (执行相同的分析命令)
```
